# St. Kizito Parish App — Engineering Audit

_Date: 2026-07-27 · Scope: `apps/mobile` (Expo SDK 55 / RN 0.83) + `apps/web` (Next.js admin) · Author: engineering audit pass_

> **Status of this document:** Findings marked **✅ Verified** were confirmed by reading the
> actual code (file:line cited). Findings marked **🔍 Needs focused pass** are informed by
> structure/naming but the internals were not yet fully read — they will be verified during
> implementation, not assumed. Nothing here is a superficial guess.

---

## 0. Executive summary

The app code is fundamentally sound — the JS bundles cleanly (`expo export` → 26 MB Hermes
bundle, zero errors), the architecture is reasonable (Expo Router + Zustand + a cache-first
data layer + a Next.js/Supabase admin). The problems are concentrated in **(a) a broken local
native build**, **(b) a handful of correctness bugs in the liturgical rendering**, and
**(c) missing production hardening** (offline dead-ends, daily refresh, safe-area).

The single most important fact: **there is no working development client yet**, so nothing can
be verified on-device until that is fixed. That is Critical-0.

## 1. Critical-0 — Development environment is broken

### 1.1 ✅ Local dev-client build fails (Gradle 9 / `IBM_SEMERU`)
`npx expo run:android` fails at `app:assembleDebug` with:

```
Class org.gradle.jvm.toolchain.JvmVendorSpec does not have member field
'org.gradle.jvm.toolchain.JvmVendorSpec IBM_SEMERU'
```

**Root cause:** `expo prebuild` generated `android/gradle/wrapper/gradle-wrapper.properties`
pinned to **Gradle 9.0.0** (`distributionUrl=...gradle-9.0.0-bin.zip`). The React Native
Gradle plugin bundled with RN 0.83 references the `JvmVendorSpec.IBM_SEMERU` toolchain-vendor
field, which the Gradle 9.0 API no longer exposes in the way the plugin expects → configuration
fails before any compilation. This is a **toolchain/version mismatch in the generated native
project**, not application code.

**Fix options (in order of preference):**
1. **Use EAS Build for the dev client** (`eas build --profile development --platform android`).
   EAS uses a controlled build image with a matched Gradle/JDK/AGP, sidestepping the local
   toolchain drift entirely. One APK installs on the emulator *and* the physical phone. This is
   the recommended path for this project because it already uses EAS and is not ejected.
2. **Pin a compatible Gradle locally.** If local builds are wanted, override the wrapper to the
   Gradle version RN 0.83 officially supports and rebuild. Because this is a CNG (managed)
   project, `android/` is regenerated by prebuild, so the pin must be applied via config
   (an Expo config plugin) rather than by hand-editing `android/`.

**Environment gaps found (needed for any local build):** `ANDROID_HOME`/`ANDROID_SDK_ROOT`
unset, `adb` not on `PATH`, no `JAVA_HOME` (only Android Studio's bundled JBR 21 exists). EAS
avoids all of these.

### 1.2 ✅ EAS build history is unhealthy
`eas build:list` shows only **two production builds, both `errored`**, and **zero development
builds**. A green development build has never existed. First milestone: produce one.

### 1.3 ✅ Stray root `app.json` (fixed during audit)
An incomplete `app.json` existed at the repo root (no name/slug/entry/plugins). Any `eas`/`expo`
command run from the repo root would pick it up and build the wrong project. It has been backed
up and removed. **Correct working directories:**
- `npm install` → **repo root** (npm workspace; installing from `apps/mobile` crashes npm 11 — see prior fix)
- `eas build`, `npx expo start --dev-client` → **`apps/mobile`** (never the repo root)

## 2. Correctness bugs (liturgical) — highest user-trust impact

For a prayer app, wrong or missing liturgical text is worse than a crash. These are Critical.

### 2.1 ✅ Daily content shows *yesterday* (#9)
`src/store/useAppStore.ts` persists `selectedDate` to AsyncStorage; `getTodayIso()` is only the
**initial** value and is overwritten by rehydrated persisted state on the next launch. There is
**no `AppState` foreground listener and no day-rollover check**, so reopening the app the next
day still shows the previously selected date's readings and office.

**Fix:** treat "today" as the default and only persist a date when the user *intentionally*
browses history. On hydration and on app-foreground (`AppState` `active`), if the selected date
isn't an explicit historical selection, snap it to `getTodayIso()`. Add a lightweight day-change
check (compare stored day to current day) so a long-lived foreground session also rolls over.

### 2.2 ✅ Responsorial Psalm drops verses / is "cut off" (#6)
`app/(tabs)/readings.tsx:307` renders `block.verses.slice(1).map(...)` — it **unconditionally
skips the first verse**. When the data shape doesn't place a throwaway/response item at index 0,
the first real strophe disappears. This is the "parts of the psalm are missing" report.

**Fix:** render verses from the actual model without `slice(1)`; drive response/verse layout off
`verse.type` (the data already carries `type: 'response' | 'verse'`) instead of positional
assumptions. Add a unit test over several psalm shapes.

### 2.3 ✅ Liturgical endings are not appended (#5)
There is no rendering logic that appends **"The word of the Lord." / "Thanks be to God."**
to First/Second readings, or **"The Gospel of the Lord." / "Praise to you, Lord Jesus Christ."**
to the Gospel. (Matches for those phrases exist only inside Divine Office *data*, not in reading
rendering.)

**Fix:** append endings at the **render layer**, keyed off `block.type` (`first_reading` /
`second_reading` / `gospel`), not by editing data. A small pure helper
`getLiturgicalClosing(blockType)` returns `{ versicle, response }`, rendered as a styled couplet
below the reading body. One place, applies everywhere, testable.

### 2.4 ✅ Text-size control doesn't scale the Psalm (or reflections) (#6/#11)
`TextSizeControl` writes `useThemeStore().textScale`. Components that read `useTheme().textScale`
scale correctly — `ReadingSection.tsx:65` (readings/gospel ✅) and `PsalmBlock.tsx:15` (office ✅).
But the **Readings-screen psalm is rendered inline with hardcoded NativeWind sizes**
(`readings.tsx:298-333`, `text-[18px]`, `leading-8`) and never reads `textScale`. Reflections
likely share this inline pattern (🔍 to confirm).

**Fix:** extract the readings psalm into a `ResponsorialPsalm` component that consumes
`textScale`/`lineHeightScale` exactly like `ReadingSection`. Audit every liturgical text surface
to ensure a single scaling source of truth. Delete the dead `src/hooks/useTextSize.ts`
(`// STUB`) so there's no ambiguity about which hook governs scaling.

## 3. UI / rendering / performance bugs

### 3.1 ✅ Bottom navigation broken on some phones (#1)
`app/(tabs)/_layout.tsx` sets `tabBarStyle: { height: spacing.tabBarHeight, paddingBottom: 8 }`
with **no safe-area inset**. Overriding the tab bar `height` to a fixed value defeats React
Navigation's automatic bottom-inset accommodation. On devices with **gesture navigation** (the
on-screen pill) or tall aspect ratios, the icons/labels are cramped or overlap the system gesture
area — exactly the "broken on some phones" report.

**Fix:** use `useSafeAreaInsets().bottom`: `height = BASE + insets.bottom`,
`paddingBottom = insets.bottom + 6`. This adapts to 3-button vs gesture nav and every device
height. Verify on a short device (e.g. Pixel 6) and a tall gesture-nav device.

### 3.2 ✅ Readings tab pills flicker (#2)
`readings.tsx` creates a **scroll ↔ layout ↔ state feedback loop**:
- `sectionOffsets` is React **state**, written by every `onLayout` (`handleSectionLayout`,
  line 82) with a fresh object.
- `onScroll` (throttle 16 ms) calls `setActiveTabId` on nearly every frame (line 98-118).
- Custom fonts (NotoSerif/Inter) load asynchronously; when they land, text metrics change →
  `onLayout` refires → `setSectionOffsets` → re-render → active-section recompute → the active
  pill flips between two sections whose offsets straddle the threshold → **flicker**.

**Fix:** move `sectionOffsets` into a `useRef` (measuring must not trigger re-render); compute the
active section from a throttled scroll handler and only `setActiveTabId` when it actually changes
(with hysteresis so it doesn't oscillate at boundaries); consider `onMomentumScrollEnd` to settle.
This removes the re-render loop and stabilizes the pills.

### 3.3 🔍 Calendar opens with lag (#8)
`app/calendar.tsx` + `src/components/calendar/*` and `src/components/liturgical/CalendarGrid.tsx`
were not yet fully read. Typical causes to verify: building the whole month (or year) eagerly on
mount, per-cell liturgical computation without memoization, non-virtualized grids, and heavy
work on the JS thread during the navigation transition. **Plan:** profile mount, memoize per-day
liturgical lookups, virtualize/lazy-render months, and defer non-critical work with
`InteractionManager` until after the screen transition.

### 3.4 🔍 Divine Office needs liturgical structure (#10)
`app/(tabs)/divine-office.tsx` and `useDivineOffice.ts` not yet fully read. The building blocks
already exist (`PsalmBlock`, `AntiphonText`, `HymnBlock`, `PrayerSection`, `PrayerBlockRenderer`,
`ScriptureQuote`). **Plan:** define a canonical office schema (Invitatory → Hymn → Psalmody with
antiphons → Reading → Responsory → Gospel Canticle → Intercessions → Lord's Prayer → Concluding
Prayer) and a single renderer that maps blocks to the existing components with liturgical
typography/spacing.

### 3.5 ✅ App size ≈ 120 MB is mostly a measurement artifact (#4)
Assets total only **4 MB**, so they are not the cause. A **universal APK** bundles multiple ABIs
(`x86_64,arm64-v8a,…`) + Hermes + all native modules → 100 MB+. The **Play Store download is not
this number**: shipping an **AAB** with per-ABI splitting delivers ~25–40 MB to each device.
**Actions:** (1) distribute an **AAB**, not a universal APK; (2) for direct-install APKs use ABI
splits / `arm64-v8a` only; (3) enable R8/Proguard resource+code shrinking for release;
(4) compress the three oversized 1.1–1.3 MB PNGs (`icon.png`, `splash-icon.png`,
`android-icon.png`) — icons should be tens of KB; (5) audit for unused deps. Hermes is already on.

### 3.6 ✅ Text-size control placement (#11)
`TextSizeControl` sits inline in the readings header row (`readings.tsx:166`) with 52×52 touch
targets (good). Improvements: guarantee no overlap with the notch/status bar on small devices,
persist the preference (it lives in `useThemeStore` — confirm that store is persisted), and reuse
the same control on every long-form reading surface (office, reflections) for consistency.

## 4. Offline / resilience

### 4.1 ✅ Donation details dead-end when offline (#7)
`useCachedData.ts` is genuinely cache-first: it loads cached data, then background-refreshes and
**does not clear cached data on fetch failure** (`refresh()` swallows errors, returns `null`,
keeps existing `data`). So once payment details have been fetched once, they survive offline. ✅

**The gap is the first-run-offline / no-cache case and the missing status signal:**
`useCachedData` exposes no `isError`/`isOffline`/`hasCache` flag, so the donation screen
(`app/donation/index.tsx`, 🔍 to read) cannot distinguish "still loading" from "offline and no
cached details." That's where the dead-end comes from.

**Fix:** extend `useCachedData` to return `{ isError, hasCache, isStale, source: 'cache'|'network' }`.
In the donation flow: use cached details when present; if no cache and offline, show a friendly
"connect to the internet to load parish account details" state; only disable **"I Have Paid"**
when details truly cannot be shown, and keep a manual retry. Persist a `lastSyncedAt` label.

### 4.2 ✅ Readings are fully offline/local
`useReadings.ts` reads from bundled local data (`getReadings`) and hardcodes
`isLoading:false, isOffline:true`. Good for reliability; note the hardcoded flags are cosmetic and
could mislead future callers — worth documenting.

## 5. New feature — Sacramental Requests (Baptismal Card first)

**Current state (✅ verified):** only `src/services/requests/requestStore.ts` exists, typed for
`donation | mass booking | thanksgiving`. No baptismal/sacrament types, no mobile screens, and the
Next.js admin (`apps/web/app/admin/*`) has pages for announcements/donations/events/mass-bookings/
mass-times/payment-details/users/feedback but **no sacramental-requests page**. This is greenfield,
but there is a clear booking/request pattern (and Supabase backend) to extend.

**Proposed architecture (extensible to Confirmation/Marriage/First Communion later):**
- **Backend (Supabase):** a single `sacrament_requests` table with `type` (enum:
  `baptismal_card`, later `confirmation`, `marriage`, …), `status`
  (`submitted|under_review|needs_info|approved|rejected`), `payload` (JSONB for
  per-type fields), `attachments`, `amount_due`, `is_free`, timestamps, and a `request_config`
  table so the admin can define, **per sacrament type**, whether it's free or has a fee and which
  fields are required. This satisfies "admin can update whether the baptismal card is free or has
  an amount, and the details required" without schema changes per new sacrament.
- **Mobile:** a generic `RequestForm` driven by the `request_config` field schema, a submit flow,
  and a status tracker (reuse the existing request/booking status UI). New route group
  `app/requests/sacraments/…`.
- **Admin (Next.js):** a `sacrament-requests` page to review, approve, reject, request more info,
  set free/fee + required fields, and trigger a notification (Expo push) back to the parishioner.
- **Notifications:** reuse the existing `expo-notifications` + notification service for status
  updates.

This is a multi-part epic and should be its own milestone after the Critical/High bug fixes.

## 6. Architecture & code-quality notes

- **Data layer is split** between `useCachedData` (AsyncStorage cache-first) and TanStack Query
  (installed, `QueryClientProvider` in `_layout.tsx`). Two caching systems coexist. Recommend
  standardizing on TanStack Query with an AsyncStorage persister for a single, observable cache
  with built-in `isError`/`isStale` — this directly solves §4.1 and reduces bespoke code.
- **Dead code:** `src/hooks/useTextSize.ts` is a `// STUB`. Remove.
- **Inline rendering vs components:** liturgical text is rendered both via components
  (`ReadingSection`, `PsalmBlock`) and inline in `readings.tsx`. The inline copies are where the
  scaling/verse bugs live. Consolidate onto the components (single source of truth).
- **Positional data assumptions** (`verses.slice(1)`) are fragile; drive rendering off explicit
  `type` fields.
- **Testing:** `jest` + `jest-expo` are configured. There are almost no tests around the
  liturgical rendering, which is the highest-risk area. Add pure-function tests for psalm
  assembly and liturgical endings before/with the fixes.

## 8. Deployment & update strategy (Expo / EAS)

1. **Delivering updates to installed apps:** two channels — **EAS Update (OTA)** for JS/asset
   changes, and **new store builds (AAB→Play)** for native changes. Wire `expo-updates` (already a
   dependency) to your EAS channels (`development`/`preview`/`production` already exist in
   `eas.json`).
2. **OTA-eligible (instant):** anything in the JS bundle or bundled assets — screens, styling,
   liturgical rendering fixes (#2/#5/#6/#9/#11), copy, images shipped in the JS bundle, most
   business logic. Ship with `eas update --channel production`.
3. **Requires a new AAB/APK (store):** any change to native code/config — adding/removing native
   modules, permissions, `app.json` native fields, app icon/splash native config, SDK upgrades,
   `expo-notifications`/`expo-sqlite` version bumps, or anything altering the native runtime.
   **Rule:** if `runtimeVersion` changes, you need a new binary.
4. **Versioning:** user-facing `version` (semver) in `app.json`; `runtimeVersion` with the
   `appVersion` policy (already set) so OTA updates only target compatible binaries; let EAS
   auto-increment Android `versionCode` (already set on the production profile).
5. **Release workflow:** `development` (dev client + `expo start`) → `preview` (internal
   distribution APK/AAB for QA on real devices) → `production` (store AAB + `production` OTA
   channel). Promote the *same* commit across channels.
6. **Rollback:** OTA — `eas update` is immutable and channel-pointed; roll back by republishing the
   previous known-good update to the channel (or `eas channel:edit` to point at the prior update).
   Binary — halt the Play staged rollout and resume the previous release. Always ship OTA to a
   small **staged rollout** first.
7. **Backend/schema migrations:** version your Supabase API responses; make the client tolerant of
   additive changes; gate breaking changes behind a `runtimeVersion` bump so old clients keep
   hitting compatible endpoints; use nullable/defaulted columns and backfill. Never ship a breaking
   API change without a matching new binary and a deprecation window.
8. **Notifying users:** a "what's new" modal keyed off the update id; for mandatory updates, a
   remote-config `minSupportedRuntimeVersion` that shows a soft/hard "please update" gate; use
   `expo-notifications` for high-value announcements.
9. **CI/CD:** GitHub Actions + EAS — on PR: typecheck/lint/`jest`; on merge to `main`:
   `eas update --channel preview`; on release tag: `eas build --profile production` +
   `eas submit` + `eas update --channel production` (staged). Use EAS build profiles already in
   `eas.json`; store the Expo token as a CI secret.
